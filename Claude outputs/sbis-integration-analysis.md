# Интеграция приложения SBL с СБИС — итоговая архитектура и план

Версия с учётом уточнённого контекста: кофейня одна (одна точка), у неё уже есть популярность и своя база постоянных клиентов (бренд — известный ювелирный), приложение ещё не запускалось в бою, оплата будет происходить прямо в приложении, тарифы СБИС уже куплены, бонусы для обычных посетителей, скорее всего, уже ведутся в СБИС. Держим в голове главную цель: приложение делают два человека без глубокого бэкенд-опыта, поэтому архитектура должна быть **простой и трудноломаемой**, а не гибкой и сложной.

## 1. Итоговое распределение ответственности

| Что | Где живёт | Почему |
|---|---|---|
| Каталог товаров, цены, остатки | **СБИС** (источник истины), зеркалится в Supabase для быстрого чтения приложением | Одна точка — синхронизация максимально простая, без риска рассинхрона между точками |
| Приём оплаты | **Платёжный шлюз** (см. раздел 2) — ни Supabase, ни сам по себе СБИС деньги с карты клиента не спишут | Оплата в приложении — это отдельный интегрируемый сервис, которого сегодня в проекте нет вообще |
| Учёт продажи / фискальный чек / списание остатка | **СБИС** | Раз всё остальное уже там — логично, чтобы факт продажи попадал туда же, а не жил только в нашей базе |
| Клиенты и бонусы | **СБИС** (её штатная бонусная программа) | У кофейни уже есть постоянные посетители и, судя по всему, действующая бонусная система в СБИС — если завести бонусы ещё и в Supabase, получится два несвязанных мира: одни клиенты копят баллы через приложение, другие (пришедшие с улицы) — нет |
| Корзина, избранное, сессия приложения | **Supabase** | Это данные конкретно приложения, СБИС про них ничего не знает и не должен |
| «Серия SBL» (стрик за визиты, геймификация) | **Supabase**, как сейчас | Это не про деньги и не про товароучёт — чисто игровая механика привязанности к приложению, СБИС тут не нужен |
| Своя кассовая панель (`kassa-terminal`) | **Выводится из эксплуатации** | Раз заказы и так должны попадать в СБИС — заказы стоит принимать штатными средствами СБИС, а не поддерживать вторую параллельную кассу на своём коде |

Из этого сразу следует хорошая новость: часть находок из прошлого аудита надёжности (риски вокруг `kassa-terminal` — загрузка Supabase SDK с CDN, неатомарность записи заказа в Supabase, отсутствие резервного опроса в кассе) **отпадают сами собой**, если эта панель выводится из эксплуатации, а не чинится.

## 2. Новый компонент, которого раньше не было в плане: платёжный шлюз

Оплата в приложении — это отдельная интеграция, требующая отдельного решения, и её стоит внести в план явно, а не как "само собой разумеющееся":

- Стандартные варианты для российского приложения: **ЮKassa**, **CloudPayments**, эквайринг через СБП (Систему быстрых платежей, обычно самая низкая комиссия). У каждого есть готовые SDK/WebView-флоу под React Native.
- **Важный вопрос на стыке оплаты и СБИС — фискализация.** По 54-ФЗ любая оплата (в т.ч. онлайн) должна сопровождаться фискальным чеком через зарегистрированную онлайн-кассу. У большинства платёжных шлюзов (например, ЮKassa) есть **встроенная фискализация** — то есть чек по онлайн-оплате может пробить сам шлюз, автоматически. Если при этом мы ЕЩЁ передаём эту же продажу в СБИС и там тоже пробивается чек — получится **задвоенный чек по одной покупке**, а это уже не мелкий баг, а нарушение с точки зрения налоговой отчётности. Это надо явно прояснить и с СБИС, и с выбранным платёжным шлюзом ДО того, как связка заработает в проде: кто именно фискализирует — шлюз или касса СБИС, и как тогда в СБИС передаётся заказ — как уже пробитая продажа (без повторной фискализации) или просто как позиция для списания остатка.
- Пока не выбран конкретный шлюз — стоит удерживаться от написания кода оплаты, чтобы не переделывать интеграцию дважды.

## 3. Что нужно спросить у СБИС теперь, когда контекст ясен

Раз тарифы уже куплены и осталось только получить доступ — вот приоритетный, сокращённый и уточнённый список (более длинный черновик из предыдущей версии документа ниже, в приложении, для справки):

1. **Приём заказа от внешнего приложения** — есть ли готовый метод API именно для передачи заказа, оформленного и оплаченного во внешнем приложении, в СБИС (по модели "заказ из интернет-магазина"), и какие статусы он поддерживает?
2. **Фискализация** — если оплата и фискальный чек уже формируются платёжным шлюзом при оплате в приложении, нужно ли (и можно ли) передавать эту продажу в СБИС БЕЗ повторной фискализации — просто для списания остатка и товароучёта?
3. **Бонусная программа** — какая бонусная программа сейчас реально работает в СБИС для очных посетителей (проценты начисления, правила списания, как идентифицируется клиент — по номеру телефона?), и есть ли API, чтобы: (а) найти/создать клиента по телефону, (б) прочитать его баланс бонусов, (в) списать/начислить бонусы при заказе из приложения по тем же правилам, что и на очной кассе.
4. **Синхронизация каталога и остатков** — периодический опрос или есть вебхук на изменение цены/остатка позиции?
5. **Тестовый контур** — есть ли песочница для обкатки без риска для боевых остатков/бонусов реальных клиентов?
6. **Лимиты API** — на нашем тарифе, и что происходит при превышении.

## 4. Обновлённый пошаговый сценарий заказа

1. Клиент открывает приложение → видит каталог, синхронизированный из СБИС.
2. Клиент оформляет заказ и **оплачивает его в приложении** через платёжный шлюз.
3. После подтверждения оплаты от шлюза (важно: именно после подтверждения, не в момент нажатия кнопки — оплата может не пройти) приложение создаёт заказ в СБИС (с учётом ответа на вопрос №2 выше про фискализацию) и параллельно — служебную запись в Supabase (для отображения статуса клиенту в реальном времени, как сейчас устроено через Realtime).
4. Бариста получает заказ через **интерфейс самой СБИС** (не через `kassa-terminal`) и готовит/выдаёт его.
5. Статус готовности/выдачи синхронизируется обратно из СБИС в Supabase (вебхук или периодический опрос), приложение показывает клиенту актуальный статус тем же механизмом, что и сейчас.
6. Бонусы — начисляются/списываются в СБИС при заказе из приложения по тем же правилам, что и на очной кассе; приложению для UI нужен только baланс на чтение.
7. **Обязательная сверка** — ежедневная/еженедельная задача, сверяющая заказы Supabase ⟷ СБИС ⟷ платежи шлюза, чтобы потерянный вебхук или сбой сети не уходил незамеченным.

## 5. Нагрузка и Supabase

Судя по ожидаемому потоку (до ~50 заказов в день) — это небольшая нагрузка, бесплатного тарифа Supabase, скорее всего, хватит ещё долго именно по объёму данных и количеству запросов. Но у бесплатного тарифа Supabase есть нюансы, которые стоит знать заранее, а не наткнуться на них внезапно:
- Бесплатный проект **автоматически приостанавливается после ~7 дней без активности** — неприятно, если это случится в проде (клиент откроет приложение, а бэкенд "уснул" и не ответит вовремя); на боевом окружении лучше сразу быть на платном тарифе, даже при низкой нагрузке, именно из-за этого поведения, а не из-за объёма данных.
- Ограничено количество одновременных realtime-подключений и логов на бесплатном тарифе — при 50 заказах в день это не должно быть проблемой, но стоит иметь это в виду при росте.

Рекомендация: для дев/тестирования — бесплатный тариф ок; для реального запуска с живыми клиентами — сразу переходить на платный, чтобы не словить "внезапно уснувший бэкенд" в самый неподходящий момент (например, вечером пятницы).

## 6. Что нужно будет доработать в приложении

- Заменить анонимную авторизацию на **реальную идентификацию по номеру телефона** (SMS-код или звонок для подтверждения) — без этого невозможно связать пользователя приложения с клиентом/бонусным счётом в СБИС, который идентифицируется по телефону.
- Вынести каталог из `data/products.js` в таблицу, синхронизируемую из СБИС.
- Вывести из эксплуатации `kassa-terminal` и самописную бонусную логику в Supabase (`bonus_accounts`/`bonus_transactions`/триггеры) — как только подтверждено, что бонусы едут через СБИС.
- Добавить интеграцию с выбранным платёжным шлюзом.
- Серверный слой (Edge Function или аналог) для вызовов к СБИС — сервисный ключ никогда не хранится в самом приложении.

## 7. Готовое письмо в СБИС (обновлено под финальный контекст)

> Добрый день! У нас одна точка продаж (кофейня), тарифы СБИС уже подключены, разрабатываем мобильное приложение, в котором клиент будет оформлять и оплачивать заказ прямо в приложении (через отдельный платёжный шлюз, ещё выбираем — ЮKassa/CloudPayments/СБП).
>
> Уточните, пожалуйста:
>
> 1. Как правильно передать в СБИС заказ, уже оформленный и оплаченный во внешнем приложении — по модели "заказ из интернет-магазина"? Нужен именно метод создания заказа/продажи через API, не только чтение каталога.
> 2. Если чек по этой оплате уже фискализируется на стороне платёжного шлюза — можно ли передать продажу в СБИС без повторной фискализации, только для списания остатка и учёта? Как это делается технически?
> 3. Какая бонусная программа сейчас работает в СБИС для наших постоянных посетителей (проценты, правила списания, идентификация по телефону)? Есть ли API, чтобы находить/создавать клиента по телефону и начислять/списывать бонусы по тем же правилам при заказе из приложения?
> 4. Как получить доступ к API (регистрация внешнего приложения, сервисный ключ) при уже подключённых тарифах — правильно понимаю, это можно оформить самостоятельно в личном кабинете (Настройки → Система → Безопасность)?
> 5. Есть ли тестовый контур для обкатки интеграции без риска для боевых остатков и реальных бонусных счетов клиентов?
>
> Заранее спасибо!

## Приложение: расширенный список вопросов (для справки, если понадобится глубже)

**По каталогу и остаткам:** как быстро остатки обновляются после продажи на кассе; есть ли вебхук на изменение цены/остатка или нужен опрос; используется ли несколько прайс-листов.

**По заказам:** резервирует ли создание заказа остаток автоматически; что происходит при возврате/отмене уже пробитого чека и как это должно отражаться в приложении; как СБИС узнаёт об отмене заказа клиентом до его исполнения.

**По клиентам и персональным данным:** какие данные обязательны для создания контрагента через CRM API (только телефон или ФИО/согласие на обработку персональных данных тоже) — это отдельно стоит уточнить у юриста/бухгалтера кофейни, если раньше персональные данные клиентов формально не собирались.

**По эксплуатации:** лимиты запросов и что при их превышении; есть ли отдельная линия поддержки именно по API-интеграциям и какой у неё SLA.
