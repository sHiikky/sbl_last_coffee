# Перенос базы данных Supabase на новый аккаунт — пошагово

Нашёл официальную документацию Supabase по этому сценарию (ссылки внизу). Формат вашего файла (`.backup.gz`, скачан из дашборда Supabase) — это обычный текстовый SQL-дамп, сжатый gzip'ом, поэтому восстанавливается через `psql`, а не через более сложный `pg_restore`.

**Важно понимать заранее:** это не просто "загрузить файл в новый проект и всё само заработает". В новый проект переносятся структура таблиц и сами данные, но НЕ переносятся: настройки Auth (в т.ч. разрешение на анонимный вход), настройки Realtime (подписки, на которых держится статус заказа и касса), Edge Functions, расширения (extensions) и API-ключи. Каждый из этих пунктов ниже — отдельный шаг, который легко забыть, и тогда что-то в приложении тихо перестанет работать уже после переезда.

## Что подготовить

1. **psql** (клиент командной строки Postgres) — скорее всего у вас его нет. Самый простой способ на Windows: скачать инсталлятор с [postgresql.org/download/windows](https://www.postgresql.org/download/windows/), запустить, оставить всё по умолчанию (он заодно поставит локальный сервер Postgres — это не мешает и не обязательно использовать, нужен только сам `psql`). После установки откройте **новое** окно PowerShell (важно — старое не увидит обновлённый PATH) и проверьте:
   ```
   psql --version
   ```

2. **Файл бэкапа без .gz** — распакуйте `db_cluster04092026121334.backup.gz` обычным архиватором (правой кнопкой → Extract/Извлечь), должен получиться файл `db_cluster04092026121334.backup` (это на самом деле текстовый SQL-файл, несмотря на расширение `.backup`).

3. **Строка подключения к новому проекту** — в новом проекте Supabase откройте Project Settings → Database → Connect → вкладка **Session pooler** (или Direct connection), скопируйте строку вида:
   ```
   postgresql://postgres.[ваш-project-ref]:[ПАРОЛЬ]@aws-0-...pooler.supabase.com:5432/postgres
   ```
   Пароль там — это пароль базы данных, который вы задавали при создании проекта (не тот "publishable key", что используется в коде приложения). Если забыли/не задавали — можно сбросить в Database Settings.

## Шаг 1 — восстановить сам дамп

В PowerShell, находясь в папке с распакованным файлом:
```
psql -d "СТРОКА_ПОДКЛЮЧЕНИЯ_ИЗ_ШАГА_ВЫШЕ" -f db_cluster04092026121334.backup
```
Выполнится не мгновенно (зависит от объёма данных). Если увидите в выводе строки `ERROR` — не паникуйте, часть ошибок безобидна (например, "role already exists" или "extension already exists"), но пришлите мне полный вывод, если ошибок много — разберём вместе, какие критичны, а какие нет.

## Шаг 2 — то, что НЕ восстановилось само (самое важное)

- **Anonymous Auth.** Приложение входит анонимно (`signInAnonymously()`) — в новом проекте это может быть выключено по умолчанию. Dashboard → Authentication → Sign In / Providers → включите **Anonymous Sign-Ins**. Без этого шага приложение вообще не сможет авторизовать ни одного клиента.
- **Realtime-публикация.** На ней держится и живой статус заказа у клиента (`OrderSuccessScreen`), и обновление доски в `kassa-terminal`. Dashboard → Database → Replication → убедитесь, что таблица `orders` (и что там ещё использовалось) включена в публикацию `supabase_realtime`. Это ровно тот тип "тихого" сбоя, который мы разбирали в прошлый раз: подключение к каналу может выглядеть рабочим, а события просто не будут приходить.
- **Расширения (extensions).** Если схема использует что-то вроде `pgcrypto` (для `gen_random_uuid()`) — Database → Extensions → сверьте, что включено в старом проекте, и включите то же самое в новом. Если каких-то расширений не хватит, восстановление на шаге 1 покажет ошибку в духе "function gen_random_uuid() does not exist" — тогда просто включите нужное расширение и повторите restore.
- **API-ключи и URL — обязательно обновить в коде приложения.** У нового проекта будут свои `SUPABASE_URL` и publishable key. Их нужно вписать в ДВА места:
  - `lib/supabaseClient.js`
  - `kassa-terminal/index.html` (строки 240–241, там отдельная, независимая копия этих же значений)

  Новые значения возьмёте в новом проекте: Project Settings → API → Project URL и Publishable key.

## Шаг 3 — что развернуть заново (Edge Functions в дамп не входят)

Если вы уже успели что-то настроить в старом проекте по нашей текущей задаче (таблицы `products`/`sync_runs`, Edge Function синхронизации) — они попадут в дамп как обычные таблицы, но саму Edge Function придётся создать в новом проекте заново (это буквально повторить шаги из `sbis-menu-integration-howto.md`, но уже в новом проекте) — функции физически не входят в дамп базы данных.

## Шаг 4 — не выключайте старый проект сразу

Проверьте в приложении на новом проекте: анонимный вход работает, оформление тестового заказа проходит, статус заказа обновляется живьём, бонусы/лояльность отображаются корректно — и только после этого можно спокойно считать старый проект нерабочим/удалять его.
