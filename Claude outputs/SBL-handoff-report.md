Дата: 10 сентября 2026
Тема: статус интеграции СБИС ↔ Supabase ↔ приложение, доступы, что делать дальше

## 1. Что сделано полностью

### Меню (Supabase → приложение)
- Таблица `products` в Supabase — единственный источник каталога для приложения. Приложение **никогда** не обращается к СБИС напрямую и не хранит его ключи.
- Edge Function `sync-sbis-catalog` — забирает каталог из СБИС и заливает в `products` (upsert по `sbis_id`). Синхронизация **только вручную по кнопке/запуску функции**, никакого автоматического крона — так решено сознательно (цены в кофейне меняются редко, лишняя нагрузка не нужна).
- Защита синхронизации:
  - дедупликация по `sbis_id` (была ошибка с дублями — исправлена);
  - новые позиции по умолчанию скрыты (`is_visible = false`), пока их не проверят вручную;
  - анти-аномалия по цене: если новая цена отличается от старой более чем в 3 раза — не обновляется автоматически, попадает в лог для ручной проверки;
  - таблица `sync_runs` — журнал каждого запуска (сколько получено/добавлено/обновлено, ошибки, ценовые аномалии);
  - Telegram-уведомление о результате синка (если настроены `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`).
- Товары-«добавки» СБИС (с префиксом `+ `) не показываются как отдельные позиции меню.
- Ручная курация поверх сырых данных СБИС (эти поля синхронизация никогда не перезаписывает):
  - `menu_category` / `menu_subcategory` — понятные покупателю разделы (Напитки/Еда/Десерты/Магазин + подкатегории), т.к. родные папки СБИС для этого слишком технические;
  - `display_name` — человеческое название товара;
  - `image_override_url` — ручная замена фото (в СБИС фото есть только у части позиций);
  - `is_modifier`, `is_visible`, `is_quick_pick`, `badge`.
- Полная разметка ~90 реальных позиций по новой таксономии (`products-menu-taxonomy.sql`, уже применена в базе).
- Экран меню в приложении полностью переделан под новую структуру: один сплошной скролл, фиксированные шапка + навигация по главным категориям (не уезжают при скролле), scroll-spy (подсветка активного раздела при ручном скролле), локальные фильтры по подкатегориям внутри раздела, облегчённые карточки без «пустых серых полей» у товаров без фото.

### Инфраструктура Supabase
- Переезд с одного проекта Supabase на другой выполнен, приложение и kassa-terminal переключены на новый проект.
- Anonymous Sign-In включён, Realtime включён для `orders`/`order_items` (нужно для статуса заказа в реальном времени).
- Найден и исправлен баг: программа лояльности начисляла «бесплатный десерт» по сырой технической категории СБИС, из-за чего в неё попадали дорогие сэндвичи (490–900 ₽) — исправлено на проверку по кураторской категории `menuCategory === 'Десерты'`.

## 2. Сделано частично

- **Синхронизация каталога** — работает, но только «каталог → приложение» (цены, наличие позиций, фото). Обратной синхронизации (заказ из приложения → СБИС) **нет**.
- **Бонусная программа** — в приложении сейчас своя, самописная логика (`loyalty/loyaltyService.js`, локальный расчёт), никак не связана с реальной бонусной программой СБИС для очных клиентов. Это два разных мира клиентов на сегодняшний день — это и есть основная незакрытая задача интеграции.
- **Идентификация пользователя** — сейчас анонимная (Supabase Anonymous Sign-In), просто чтобы у пользователя был `auth.uid()` для заказов. Для связки с СБИС (клиент/бонусы обычно идентифицируются по телефону) этого недостаточно.
- **Схема заказов** — заказы пишутся в Supabase (`orders`/`order_items`), но нигде не передаются в СБИС. Кассир/учёт в СБИС о заказах из приложения не узнают.
- **Классификация каталога** — 3 позиции СБИС остались неразмеченными по таксономии (нужно уточнить у кофейни, что это): «Кедровая сказка», «Шоковзлёт», «Очень странные дела по-сибирски».
- **Раздел «Магазин»** — размечен в таксономии, но выключен (`is_visible = false`) — решение, включать ли его, ещё не принято.

## 3. Что осталось сделать (по приоритету для интеграции СБИС)

1. **Получить/уточнить у СБИС:**
   - есть ли API для бонусной программы (найти/создать клиента по телефону, прочитать баланс, списать/начислить бонусы по тем же правилам, что на очной кассе);
   - есть ли API для передачи заказа из приложения в СБИС (создание документа продажи/чека);
   - есть ли тестовый (sandbox) контур, чтобы не тестировать на боевых остатках/бонусах реальных клиентов;
   - `pointId` (точка продаж), если ещё не зафиксирован.
2. **Заменить анонимную авторизацию на идентификацию по номеру телефона** (SMS-код) — без этого нельзя связать пользователя приложения с клиентом СБИС.
3. **Передача заказа в СБИС** после оплаты в приложении (сначала в тестовый контур, если он есть).
4. **Чтение/списание бонусов через СБИС** вместо самописной логики в `loyalty/loyaltyService.js` — как только подтверждено, что API есть. После этого старую бонусную логику и `kassa-terminal` можно выводить из эксплуатации.
5. **Обратная синхронизация статуса заказа** СБИС → Supabase → приложение (сейчас Realtime уже настроен на стороне Supabase, не хватает только источника обновлений от СБИС).
6. **Ежедневная сверка** Supabase / СБИС / платежей — обнаружить рассинхрон на малом числе тестовых заказов сильно дешевле, чем на потоке боевых.
7. Мелкое по каталогу: доразметить 3 позиции выше, решить судьбу раздела «Магазин».

Подробный разбор вопросов к СБИС и общая архитектура — в файлах `sbis-integration-analysis.md`, `sbis-catalog-findings.md`, `sbis-menu-integration-howto.md`, `sbis-sync-reliability-recommendations.md` (переданы вместе с этим отчётом).
