Последний пакет SQL: параллельное оформление.
Проект vxefueynagwuavlyeiqc; SQL Editor, роль postgres.

1. Запустить 01-setup.sql один раз. Будут сохранены два помеченных тестовых клиента с балансом по 30 и временный товар [SQL TEST ...] с ценой 100. Существующие товары СБИС не изменяются.
2. Подготовить ДВЕ вкладки браузера с SQL Editor: заново скопировать обновлённые 02-same_key-A.sql и 03-same_key-B.sql (Revision 2). Запустить B, затем в течение 35 секунд A. B дождётся сигнала готовности A и только затем отправит запрос. Дождаться DONE у обоих.
3. Запустить 04-verify-same-key.sql. Ожидаются 8 PASS: один заказ, один состав, одно списание 20, баланс 10, одинаковый id в ответах.
4. Заново скопировать в две вкладки обновлённые 05-overspend-A.sql и 06-overspend-B.sql (Revision 2). Аналогично запустить B, затем в течение 35 секунд A. В B корректный отказ BONUS_BALANCE_CHANGED обрабатывается тестом: итог DONE ожидаем.
5. Запустить 07-verify-overspend.sql. Ожидаются 8 PASS: один заказ на 20 бонусов принят, второй отклонён без лишнего заказа/списания.
6. После завершения всех A/B запустить 08-cleanup.sql. Ожидается PASS; тестовые пользователи, заказы и товар будут удалены.

Во время теста не заказывать [SQL TEST] товар и не менять тестовые заказы в кассе.
При ошибке пришлите её; не повторяйте setup поверх существующих тестовых записей. Для отмены теста дождитесь завершения A/B и запустите cleanup.
Пересечение запросов подтверждается pg_blocking_pids, а не только временем выполнения.
Служебный advisory-lock сигнализирует B, что A уже держит прикладные блокировки. B только наблюдает этот сигнал, не захватывает его. Сигнал не создаёт искусственную конкуренцию вместо блокировок приложения.
После старого неудачного прогона сначала дождаться завершения обоих запросов, выполнить 08-cleanup.sql и затем 01-setup.sql; старый заказ нельзя использовать как подтверждение параллельного создания.
Проверяется серверный SQL-путь, а не HTTP/мобильный интерфейс. Пропуски в номерах заказов допустимы; последовательности не сбрасываются.
